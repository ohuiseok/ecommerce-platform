# ADR-009: 상품 목록 캐시 key 전략과 TTL

## 상태

Accepted

## 배경

상품 목록 조회는 `GET /api/products`, 카테고리, 브랜드, 가격 범위, 키워드 검색처럼 필터와 정렬, 페이지 조합이 많다. Phase 2 Day 15에서 활성 상품 목록과 주요 필터 조회에 복합 인덱스를 추가했지만, 상품 수와 조회 트래픽이 늘면 같은 목록 조합을 반복 조회하면서 DB 부하가 커질 수 있다.

반면 목록 캐시는 key 조합이 빠르게 늘고, 가격, 판매 상태, 재고 같은 변경이 사용자에게 늦게 반영될 수 있다. 특히 현재 모델은 주문 생성 시 재고를 즉시 차감하므로 재고 수량을 긴 TTL로 캐시하면 품절 상품이 계속 노출될 수 있다.

따라서 캐시를 즉시 도입하기보다, 도입을 검토할 성능 기준과 캐시 대상, key 구성, TTL, 무효화 원칙을 먼저 정한다.

## 결정

상품 목록 캐시는 기본 비활성 상태로 두고, 운영 지표가 기준을 넘을 때 제한적으로 도입한다. 초기 캐시는 사용자용 활성 상품 목록 중 반복 조회가 많은 조합만 대상으로 한다.

| 항목 | 결정 |
| --- | --- |
| 도입 조건 | 상품 목록 p95 300ms 초과 또는 DB CPU 70% 이상이 10분 지속될 때 검토 |
| 초기 대상 | 활성 상품 기본 목록, 카테고리별 목록, 브랜드별 목록, 가격 범위 목록 |
| 제외 대상 | 키워드 부분 문자열 검색, 재고 부족 관리자 조회, 상품 상세 조회 |
| 캐시 key | 조회 타입, 필터 값, page, size, sort를 정규화해 구성 |
| 기본 TTL | 60초 |
| 최대 TTL | 5분을 넘기지 않음 |
| 무효화 | 상품 생성, 수정, 삭제, 판매 상태 변경, 가격 변경 시 관련 목록 캐시 삭제 |
| 재고 수량 | 목록 캐시 신선도 위험을 줄이기 위해 긴 TTL 캐시 판단에 사용하지 않음 |

캐시는 DB 인덱스와 쿼리 튜닝 이후에도 조회 부하가 남을 때 적용한다. 현재 단계에서는 캐시 인프라나 `@Cacheable` 구현을 추가하지 않고, 이후 구현 작업의 기준으로 이 ADR을 사용한다.

## 캐시 도입 기준

아래 조건 중 하나가 운영 또는 운영 유사 부하 테스트에서 확인되면 목록 캐시를 검토한다.

- 상품 목록 계열 API의 p95 응답 시간이 300ms를 초과한다.
- 상품 목록 조회로 인한 DB CPU 사용률이 70% 이상으로 10분 이상 지속된다.
- 동일한 필터와 정렬, 첫 페이지 요청이 짧은 시간에 반복되어 DB 조회 중복이 명확하다.

단일 느린 쿼리나 키워드 검색 병목은 먼저 실행 계획과 인덱스를 점검한다. 특히 `LOWER(... LIKE '%keyword%')` 검색은 목록 캐시보다 PostgreSQL `pg_trgm` 또는 검색 read model 검토가 더 적합할 수 있다.

## 캐시 대상

초기 대상은 사용자에게 노출되는 활성 상품 목록 중 key 공간을 통제할 수 있는 조회로 제한한다.

| 조회 | 캐시 여부 | 이유 |
| --- | --- | --- |
| 전체 활성 상품 목록 | 캐시 후보 | 첫 페이지와 기본 정렬 반복 조회 가능성이 높다. |
| 카테고리별 목록 | 캐시 후보 | 카테고리 수가 제한적이면 key 증가를 통제할 수 있다. |
| 브랜드별 목록 | 캐시 후보 | 인기 브랜드 중심으로 반복 조회가 생길 수 있다. |
| 가격 범위 목록 | 제한적 후보 | 가격 구간이 자유 입력이면 key가 폭증하므로 표준 구간이 있을 때만 적용한다. |
| 키워드 검색 | 제외 | keyword 자유도가 높고 부분 문자열 검색 특성상 캐시 효율이 낮다. |
| 재고 부족 조회 | 제외 | 관리자 운영성 조회이며 신선도가 더 중요하다. |
| 상품 상세 조회 | 제외 | ADR-010에서 별도 정책으로 결정한다. |

캐시 대상은 인기 조합부터 좁게 시작한다. 전체 필터 조합을 모두 캐시하지 않는다.

## 캐시 key 정책

캐시 key는 같은 의미의 요청이 같은 key를 사용하도록 정규화한다.

기본 형식은 다음과 같다.

```text
product:list:{type}:status=ACTIVE:{filters}:page={page}:size={size}:sort={sort}
```

정규화 기준은 다음과 같다.

- `type`은 `all`, `category`, `brand`, `price-range`처럼 조회 경로를 명확히 구분한다.
- 카테고리와 브랜드는 앞뒤 공백을 제거하고 대소문자 정책을 서비스 조회와 맞춘다.
- `page`, `size`, `sort`는 Spring `Pageable`에 실제 적용된 값을 사용한다.
- 정렬 값이 없으면 기본 정렬을 명시해 key를 흔들리지 않게 한다.
- 가격 범위는 자유 입력을 그대로 캐시하지 않고, 표준 구간이 정의된 경우에만 key로 사용한다.

key에는 사용자 ID, traceId, 요청 시각처럼 목록 결과에 영향을 주지 않는 값을 넣지 않는다. 개인화 가격이나 사용자별 쿠폰 노출이 상품 목록에 들어가면 해당 응답은 공용 캐시 대상에서 제외한다.

## TTL과 무효화 정책

기본 TTL은 60초로 둔다. 목록 조회가 매우 뜨거운 조합이라도 최대 TTL은 5분을 넘기지 않는다.

상품 목록 캐시는 아래 변경이 발생하면 관련 key를 삭제한다.

- 상품 생성
- 상품명, 설명, 카테고리, 브랜드 변경
- 가격 변경
- 판매 상태 변경
- 상품 삭제 또는 비활성화

재고 변경은 주문마다 빈번하게 발생하므로 모든 목록 캐시를 즉시 삭제하면 캐시 효율이 사라질 수 있다. 따라서 초기 목록 캐시는 재고 수량을 강하게 신뢰해야 하는 화면에 쓰지 않고 짧은 TTL로만 보호한다. 품절 여부 노출 정확도가 중요한 화면은 상세 조회 또는 주문 생성 시점의 재고 검증을 최종 기준으로 둔다.

## 적용 범위

- 현재 구현 단계에서는 캐시 코드를 추가하지 않는다.
- Phase 2 이후 상품 목록 캐시를 구현할 때 이 ADR의 도입 조건, key 정책, TTL을 따른다.
- 키워드 검색 성능은 ADR-011의 검색 read model 도입 기준과 함께 검토한다.
- 상품 상세 캐시는 ADR-010에서 별도로 결정한다.
- 캐시 저장소는 초기에는 애플리케이션 로컬 캐시 또는 Redis 중 운영 환경에 맞게 선택하되, 다중 인스턴스 배포에서 일관성이 필요하면 Redis를 우선 검토한다.

## 결과

상품 목록 캐시는 성능 문제가 관측될 때 제한적으로 도입한다. key는 조회 타입, 필터, 페이지, 정렬을 정규화해 구성하고, TTL은 기본 60초로 짧게 유지한다.

이 결정은 캐시 key 폭증과 재고 신선도 저하를 피하면서, 반복 조회가 실제 병목으로 확인될 때 빠르게 캐시 구현으로 이어질 기준을 제공한다.
