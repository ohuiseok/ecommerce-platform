# ecommerce-platform 포트폴리오 고도화 로드맵

## 작성 기준

이 문서는 현재 `ecommerce-platform` 코드베이스를 모놀리식/모듈러 모놀리식으로 유지한다는 전제에서 작성한다. 목표는 서비스 분리가 아니라, 현재 도메인 경계를 더 명확히 하고 실제 이커머스 운영에서 자주 발생하는 동시성, 일관성, 장애 복구 문제를 단계적으로 보강하는 것이다.

아래 내용은 코드에서 확인한 현재 구현, 한계, 개선 방향을 분리한다. 현재 구현에 없는 기능은 명시적으로 "한계" 또는 로드맵의 개선 작업으로 표시한다.

## 현재 코드 분석

### 상품·재고

- 현재 사실: 재고 차감은 `ProductRepository.decreaseStockIfAvailable`의 native 조건부 `UPDATE`로 처리한다. `status = 'ACTIVE'`와 `stock_quantity >= quantity` 조건을 DB에 위임하므로, 동일 상품에 주문이 동시에 몰려도 음수 재고로 내려가는 문제는 쿼리 레벨에서 방어한다.
- 현재 사실: 재고 복구는 `increaseStock`으로 수량을 더하고, 상품 상태가 `OUT_OF_STOCK`이면 `ACTIVE`로 되돌린다. 주문 취소 흐름에서 이 복구 로직을 호출한다.
- 한계: 현재 방어는 애플리케이션이 호출하는 조건부 UPDATE에 의존한다. DB `CHECK (stock_quantity >= 0)` 제약이나 재고 변경 원장은 아직 없어, 다른 쓰기 경로가 생기면 같은 불변식을 별도로 보강해야 한다.
- 한계: 재고는 주문 생성 시 즉시 차감된다. 결제 실패, 결제창 이탈, PG 응답 지연이 길어지는 경우를 위한 TTL 기반 예약 재고와 만료 복구 흐름은 아직 없다.
- 한계: 상품 목록과 검색은 pageable DB 조회와 `LIKE` 검색 중심이다. 캐시, 검색 read model, 캐시 무효화 정책은 아직 없다.

### 주문

- 현재 사실: `OrderService.createOrder`와 `createOrderFromCart`는 하나의 로컬 트랜잭션 안에서 사용자 확인, 상품 조회, 재고 차감, 주문 금액 계산, 쿠폰 할인 계산, 주문 저장, 쿠폰 사용 처리를 수행한다.
- 현재 사실: 주문 생성에는 현재 PG 호출이 직접 포함되지 않는다. 결제 호출은 `PaymentService`에서 별도로 수행된다.
- 현재 사실: 주문 취소는 `SHIPPED`, `DELIVERED` 상태만 거부하고, 취소 성공 시 재고와 쿠폰을 복구한다.
- 한계: 주문 상태는 `PENDING`, `CONFIRMED`, `PROCESSING`, `SHIPPED`, `DELIVERED`, `CANCELLED`로 존재하지만, 허용 전이를 명시한 상태 머신은 없다. `updateOrderStatus`는 요청 문자열을 enum으로 바꾼 뒤 바로 상태를 변경하므로 운영자 API가 잘못 호출되면 비정상 전이가 가능하다.
- 한계: 부분 취소, 부분 환불, 라인 단위 상태, 쿠폰 할인 배분 정책은 아직 없다.

### 결제

- 현재 사실: `PaymentService.requestPayment`는 클래스 레벨 `@Transactional` 흐름 안에서 `MockPgClient.charge`를 동기로 호출한다. Mock PG는 카드번호 마지막 숫자가 홀수이면 실패를 반환하고, 성공 시 `MOCK-...` 형식의 거래 ID를 반환한다.
- 현재 사실: 동일 주문에 대해 이미 `COMPLETED` 결제가 있으면 중복 결제를 거부한다. 다만 실패 결제나 처리 중 재시도를 같은 요청으로 묶는 idempotency key는 없다.
- 현재 사실: 결제 성공 후 `orderService.markOrderConfirmed`를 호출해 주문을 `CONFIRMED`로 바꾼다.
- 한계: 실제 PG로 바뀌면 외부 I/O를 DB 트랜잭션 내부에서 수행하는 구조가 된다. 외부 승인은 성공했지만 DB 트랜잭션이 롤백되거나, 결제 row 저장 후 주문 확정이 실패하거나, 서버 응답 타임아웃으로 사용자가 재시도하는 경우 과금과 주문 상태가 어긋날 수 있다.
- 한계: 결제 취소는 내부 상태를 `CANCELLED`로 변경하는 수준이다. 실제 PG 환불 호출, 환불 idempotency, 주문 취소와 결제 취소의 보정 흐름은 아직 없다.

### 쿠폰

- 현재 사실: 쿠폰 발급 수량 제한은 `CouponRepository.incrementIssuedCountIfAvailable`의 조건부 `UPDATE`로 처리한다. `issue_limit IS NULL OR issued_count < issue_limit` 조건을 DB에서 검사하므로 전체 발급 한도 초과는 비교적 안전하게 막는다.
- 현재 사실: 사용자별 중복 발급은 `user_coupons` 테이블의 `user_id`, `coupon_id` 유니크 제약이 최종 방어선이다.
- 한계: 발급 흐름은 `existsByUserIdAndCoupon_CouponId` 확인 후 `issuedCount` 증가, `UserCoupon` 저장 순서다. `issuedCount` 증가와 `UserCoupon` 저장은 같은 트랜잭션 안에 있으므로 정상 롤백되면 증가분도 되돌아갈 수 있지만, 동일 사용자 동시 발급은 유니크 제약 예외와 롤백 동작에 의존하므로 동시성 테스트로 검증해야 한다.
- 현재 사실: 쿠폰 사용은 `calculateDiscount`에서 `ISSUED` 상태를 확인한 뒤, 주문 저장 후 `markUsed`에서 엔티티의 `use(orderId)`를 호출해 `USED`로 바꾼다.
- 한계: 쿠폰 사용 처리는 `WHERE status = 'ISSUED'` 조건부 업데이트가 아니다. 같은 `UserCoupon`을 동시에 두 주문에 사용하는 경쟁 상황에서는 할인 계산과 사용 처리 사이의 구간이 열려 있다.
- 한계: 쿠폰 스태킹, 상품·카테고리 제한, 부분 취소 시 할인 재배분과 복구 정책은 아직 없다.

### 이벤트·관측성

- 현재 사실: 도메인 간 처리는 서비스 메서드 직접 호출 중심이다. 모놀리식에서는 단순하고 디버깅하기 쉬운 장점이 있다.
- 한계: 알림, 검색 인덱싱, 정산 이벤트처럼 저장 후 비동기로 처리해야 하는 후속 작업을 위한 Outbox 패턴은 아직 없다.
- 한계: traceId 기반 구조화 로그, 도메인별 에러율·지연시간 지표, SLO 대시보드는 아직 명확하지 않다.

| Day 1: 주문 상태 전이표를 문서로 작성한다. | 현재는 enum만 있고 어떤 상태에서 어떤 상태로 갈 수 있는지 코드와 문서에 고정되어 있지 않다. 결제 확정, 배송 시작, 취소 요청이 늘어나면 비정상 전이를 막기 어렵다. | 먼저 문서화하면 구현 전 논의 비용이 들지만, 이후 상태 변경 로직의 기준점이 생긴다. | 필요 - ADR-001: 주문 상태 전이 정책과 예외 허용 범위를 결정 |

| Day 3: 결제 idempotency key 정책 ADR을 작성한다. | 사용자 새로고침, 앱 재시도, PG 응답 지연은 같은 결제 요청을 여러 번 발생시킨다. 같은 요청을 같은 결과로 묶기 위한 식별자 정책이 먼저 필요하다. | 클라이언트 생성 key는 재시도 의미가 명확하지만 클라이언트 구현 책임이 생긴다. 서버 생성 key는 클라이언트 부담이 작지만 동일 요청 판별이 약해질 수 있다. | 필요 - ADR-002: `idempotencyKey` 전역 unique, `userId + key`, `orderId + key` 중 적용 scope와 보관 기간을 결정 |

| Day 6: 쿠폰 사용을 `ISSUED` 상태 조건부 업데이트로 변경한다. | 할인 계산 후 사용 처리 사이의 경쟁 구간을 줄여야 동일 쿠폰 중복 사용을 막을 수 있다. DB가 `ISSUED` 상태를 원자적으로 확인하고 `USED`로 변경해야 한다. | 엔티티 변경 중심 코드보다 리포지토리 업데이트 쿼리가 늘어난다. 대신 동시성 방어 책임이 명확해진다. | 불필요 - 구현 세부 보강이며 정책 선택지가 크지 않음 |
| Day 7: 결제-주문 불일치 조회 쿼리를 만든다. | 결제는 완료인데 주문이 `CONFIRMED`가 아니거나, 주문은 확정인데 결제 row가 없는 상태를 빠르게 찾을 수 있어야 한다. 자동 보정 전이라도 운영자가 확인할 기준이 필요하다. | 보정은 하지 않고 탐지만 하므로 즉시 문제를 해결하지는 못한다. 대신 위험한 자동 수정 전에 데이터 패턴을 볼 수 있다. | 불필요 - 운영 조회 기능이며 아키텍처 결정은 작음 |
| Day 8: traceId를 MDC에 넣고 주문·결제·쿠폰 로그 필드를 통일한다. | 장애 시 주문번호, 결제번호, 사용자 ID를 기준으로 흐름을 이어서 추적할 수 있어야 한다. 현재 로그는 일부 도메인 이벤트만 남기므로 장애 분석에 필요한 공통 필드가 부족하다. | 로그량이 늘고 개인정보 마스킹 기준이 필요하다. 초기에 최소 필드만 정하면 비용을 통제할 수 있다. | 필요 - ADR-003: 로그 필드, 마스킹 기준, traceId 전달 방식을 결정 |
| Day 9: 재고·쿠폰·결제 idempotency 최소 동시성 테스트를 추가한다. | Phase 1에서 바꾸는 조건부 업데이트와 idempotency 로직은 경쟁 상황에서 검증해야 의미가 있다. 재고 초과 차감 방지, 동일 쿠폰 중복 사용 방지, 같은 결제 key 재요청 결과 반환을 우선 검증한다. | 테스트 시간이 늘 수 있으므로 작은 데이터셋과 명확한 반복 횟수로 시작한다. 광범위한 부하 테스트는 Phase 2에서 별도로 확장한다. | 불필요 - Phase 1 변경의 회귀 방지 테스트 |

## Phase 2: 운영 고도화

| 작업 | 왜 필요한가 | 트레이드오프 | ADR 필요 여부 |
| --- | --- | --- | --- |
| Day 1: 즉시 차감 유지안과 TTL 예약 재고안을 비교하는 ADR 초안을 작성한다. | 현재 즉시 차감은 단순하지만 결제 실패와 이탈 시 재고 복구에 의존한다. Phase 2의 복구 작업은 우선 즉시 차감을 유지한다는 전제에서 진행하고, TTL 예약 재고는 도입 조건을 따로 정한다. | 구현 단순성은 즉시 차감이 유리하고, 장애 복구와 사용자 경험은 예약 재고가 유리하다. 예약 재고를 바로 도입하지 않더라도 전환 기준을 남겨두면 이후 판단이 흔들리지 않는다. | 필요 - ADR-004: 즉시 차감 유지와 TTL 예약 재고 중 기본 정책 및 전환 조건을 결정 |
| Day 2: 결제 실패 시 주문 상태 전이와 재고·쿠폰 복구 정책을 정한다. | 현재 실패 결제가 발생해도 주문은 `PENDING`으로 남는다. 재고와 쿠폰만 복구하면 살아 있는 주문과 복구된 자원이 충돌할 수 있으므로, `PAYMENT_FAILED` 추가 또는 `CANCELLED` 전이 중 하나를 먼저 정해야 한다. | `PAYMENT_FAILED`는 결제 실패를 명확히 표현하지만 주문 상태 enum, API 응답, 상태별 조회, 기존 테스트에 영향이 있다. `CANCELLED`는 단순하지만 사용자 취소와 결제 실패를 구분하기 어렵다. | 필요 - ADR-005: 결제 실패 주문의 목표 상태와 복구 트랜잭션 범위를 결정 |
| Day 3: 결제 실패 주문 상태 전이와 재고·쿠폰 복구를 같은 트랜잭션으로 구현한다. | 결제가 명확히 실패한 경우에는 주문 상태를 실패 또는 취소 상태로 바꾸고, 같은 트랜잭션에서 재고와 쿠폰을 idempotent하게 복구해야 한다. 그래야 중복 호출이나 재시도에도 재고가 중복 증가하지 않는다. | 실패 결과가 확정된 경우만 처리하면 보수적이지만 PG 응답 불명 상태까지 해결하지는 못한다. 타임아웃 복구는 별도 단계로 분리한다. | 불필요 - Day 2 ADR에서 정한 정책의 구현 작업 |
| Day 4: PENDING 주문 만료 기준 ADR을 작성한다. | 결제창 이탈이나 응답 지연으로 주문이 오래 대기 상태에 남을 수 있다. 얼마 동안 대기시킬지 기준이 없으면 재고 잠김과 늦은 결제 성공 처리 기준이 흔들린다. | 만료 시간을 짧게 잡으면 판매 가능 재고 회전은 빨라지지만 늦은 결제 성공과 충돌할 수 있다. 길게 잡으면 고객 경험은 안정적이지만 재고가 오래 묶인다. | 필요 - ADR-008: 결제 대기 만료 시간과 늦은 결제 성공 처리 정책을 결정 |
| Day 5: 만료 주문 재고·쿠폰 복구 스케줄러를 구현한다. | PENDING 만료 기준이 정해지면 주기적으로 오래된 주문을 찾아 재고와 쿠폰을 복구해야 한다. 수동 운영 없이 묶인 자원을 회수하는 최소 장치다. | 스케줄러 중복 실행을 고려해야 한다. 복구 작업은 idempotent하게 만들어야 재실행 시 재고가 중복 증가하지 않는다. | 불필요 - Day 4 ADR에서 정한 정책의 구현 작업 |
| Day 6: Mock PG 이벤트 모델을 정의한다. | 실제 PG 웹훅을 바로 붙이기 전, 성공·실패·취소·중복 전달 이벤트를 로컬에서 재현할 수 있어야 한다. 현재 Mock PG는 동기 응답만 제공한다. | Mock이 실제 PG를 완전히 대체하지는 못한다. 그러나 웹훅 처리와 idempotency 테스트를 빠르게 만들 수 있다. | 불필요 - 테스트용 이벤트 모델이며 외부 계약이 아님 |
| Day 7: 늦게 도착한 결제 성공 이벤트를 운영 보정 대상으로 등록한다. | 주문 만료 후 PG 성공 이벤트가 늦게 도착할 수 있다. 현재 실제 PG 환불 연동은 없으므로 우선 환불 필요 상태로 마킹하고 운영 보정 목록에 올리는 단계가 현실적이다. | 즉시 자동 환불보다 구현 범위는 작지만 운영 개입이 필요하다. 추후 PG 환불 API가 붙으면 이 상태를 기준으로 자동화를 확장할 수 있다. | 불필요 - Day 4 ADR에서 정한 정책의 단계적 구현 |
| Day 8: 웹훅 idempotency 저장소를 추가한다. | PG 웹훅은 같은 이벤트를 여러 번 보낼 수 있다. 이벤트 ID 또는 거래 ID 기준으로 이미 처리한 웹훅을 재처리하지 않아야 한다. | 저장소가 하나 늘고 보관 기간 정책이 필요하다. 대신 중복 상태 변경과 중복 환불 위험을 줄인다. | 필요 - ADR-006: 웹훅 중복 판단 키와 보관 기간을 결정 |
| Day 9: 웹훅 상태 반영 로직과 재시도 테스트를 작성한다. | 결제 결과가 API 응답보다 웹훅으로 늦게 도착할 수 있다. 최종 상태를 idempotent하게 반영하고, 같은 이벤트 재전송에도 결과가 변하지 않아야 한다. | 상태 반영 규칙이 주문 상태 머신과 결합된다. 테스트가 늘어나지만 결제 장애 회복력을 검증할 수 있다. | 불필요 - Day 8 ADR과 주문 상태 정책의 구현 작업 |
| Day 10: Outbox 테이블 스키마를 설계한다. | `OrderCreated`, `PaymentCompleted`, `PaymentFailed`, `OrderCancelled` 같은 저장 결과를 알림·검색 인덱싱·정산 후속 처리로 안정적으로 넘기려면 이벤트 저장소가 필요하다. 내부 도메인 호출을 대체하려는 목적은 아니다. | Outbox는 테이블과 배치 관리 비용이 생긴다. 대신 DB 저장과 이벤트 발행 사이의 이중 쓰기 문제를 줄인다. 쿠폰 사용 이벤트는 정산·프로모션 분석 요구가 생길 때 포함 여부를 결정한다. | 필요 - ADR-007: Outbox 적용 이벤트 범위와 보관 정책을 결정 |
| Day 11: 주문·결제 저장 트랜잭션 안에서 Outbox 이벤트를 함께 저장한다. | 핵심 상태 변경과 이벤트 기록이 같은 로컬 트랜잭션에 들어가야 한쪽만 성공하는 상태를 줄일 수 있다. | 서비스 메서드에 이벤트 기록 코드가 추가된다. 도메인 이벤트 생성 위치를 일관되게 정해야 한다. | 불필요 - Day 10 ADR에서 정한 범위의 구현 작업 |
| Day 12: Outbox 발행 대상 조회와 성공 상태 업데이트를 구현한다. | 저장된 이벤트를 후속 처리 대상으로 가져오고, 발행 성공 시 다시 발행되지 않게 상태를 바꿔야 한다. Outbox 워커의 가장 작은 정상 경로다. | 조회 배치 크기와 락 전략을 정해야 한다. 단순 조회는 쉽지만 다중 인스턴스에서 중복 발행 가능성이 있다. | 불필요 - 발행 워커의 기본 구현 작업 |
| Day 13: Outbox 실패 retry count 증가와 dead-letter 전환을 구현한다. | 일시적 실패는 재시도하고, 반복 실패는 운영자가 확인할 수 있게 격리해야 한다. 실패 상태가 없으면 워커가 무한 재시도하거나 조용히 유실될 수 있다. | retry 기준이 과하면 후속 시스템에 부하를 주고, 너무 낮으면 복구 가능한 이벤트가 dead-letter로 빠진다. | 필요 - ADR-007: 최대 재시도 횟수와 dead-letter 전환 기준을 결정 |
| Day 14: Outbox 소비자 idempotency 기준을 정의한다. | 발행자는 장애 상황에서 같은 이벤트를 두 번 보낼 수 있다. 소비자가 이벤트 ID 기준으로 중복 처리를 막아야 전체 흐름이 안전해진다. | 모든 소비자에 idempotency 저장소나 처리 이력이 필요할 수 있다. 대신 at-least-once 발행 모델을 현실적으로 운영할 수 있다. | 필요 - ADR-007: 소비자별 중복 판단 키와 보관 기간을 결정 |
| Day 15: 상품 검색 쿼리와 DB 인덱스 튜닝 후보를 점검한다. | 캐시나 검색 read model을 검토하기 전에 현재 DB 검색의 병목을 먼저 확인해야 한다. 카테고리, 브랜드, 상태, 가격 범위, 정렬 기준에 맞는 인덱스와 실행 계획을 보는 것이 더 보수적인 첫 단계다. | DB 튜닝은 카테고리·브랜드·상태·가격·정렬 조건에는 효과가 있을 수 있지만, 현재 `LOWER(... LIKE '%keyword%')` 형태의 부분 문자열 검색은 일반 B-tree 인덱스 효과가 제한적이다. | 불필요 - 현재 DB 검색을 먼저 개선하는 구현·분석 작업 |
| Day 16: 상품 목록 캐시 초기 기준안을 작성한다. | 상품 목록은 필터, 정렬, 페이지 조합이 많아 DB 부하가 먼저 커질 수 있다. 초기 기준안으로 목록 p95 300ms 초과 또는 DB CPU 70% 이상이 10분 지속되면 캐시를 검토한다. | 필터·정렬·페이지 조합에 따라 캐시 key가 폭발할 수 있다. 인기 조합만 캐시하거나 TTL을 짧게 두는 보수적 접근이 필요하다. | 필요 - ADR-009: 목록 캐시 대상, key 전략, TTL을 결정 |
| Day 17: 상품 상세 캐시와 무효화 기준을 작성한다. | 상세 조회는 반복 접근이 많고 캐시 효율이 높을 수 있다. 가격, 재고, 판매 상태 변경 시 언제 무효화할지 정해야 잘못된 상품 정보를 줄일 수 있다. | 상세 캐시는 목록보다 key는 단순하지만 재고 신선도 요구가 높다. 재고는 캐시에서 제외하거나 짧은 TTL로 분리하는 선택이 필요하다. | 필요 - ADR-010: 상세 캐시 필드 범위와 무효화 시점을 결정 |
| Day 18: 버스트 주문, PG 실패, DB 지연 통합 테스트를 추가한다. | Phase 1의 최소 동시성 테스트를 운영 장애 패턴으로 확장한다. PG 실패율 증가, DB 지연, 주문 버스트 상황에서 재고·쿠폰·결제 상태가 오래 어긋나지 않는지 확인한다. | 테스트 시간이 길어질 수 있다. 핵심 시나리오를 별도 profile로 분리하면 개발 속도와 신뢰성을 균형 있게 가져갈 수 있다. | 불필요 - 신뢰성 검증 확장 작업이며 정책 결정이 아님 |

## Phase 3: 아키텍처 확장

| 작업 | 왜 필요한가 | 트레이드오프 | ADR 필요 여부 |
| --- | --- | --- | --- |
| Day 1: 검색 read model 도입 조건을 정의한다. | Phase 2의 DB 인덱스와 쿼리 튜닝 이후에도 검색 병목이 남는 경우에만 별도 read model을 검토해야 한다. 초기 기준안으로 상품 10만 건 이상, 검색 p95 300ms 초과, 검색 쿼리로 DB CPU 70% 이상이 10분 지속되면 OpenSearch 같은 대안을 검토한다. | 검색 인덱스는 성능과 검색 품질을 높이지만 동기화 지연과 운영 비용이 생긴다. 기준 없이 도입하면 포트폴리오에서도 과설계로 보일 수 있다. | 필요 - ADR-011: DB 검색 유지와 검색 read model 도입 기준을 결정 |
| Day 2: 검색 인덱스 동기화 이벤트를 Outbox 기반으로 설계한다. | 검색 read model을 도입한다면 상품 변경과 인덱스 반영 사이의 유실을 막아야 한다. Outbox를 쓰면 상품 저장과 인덱싱 이벤트 기록을 같은 트랜잭션으로 묶을 수 있다. | 검색 결과는 eventual consistency가 된다. 사용자에게 허용 가능한 지연 시간을 정해야 한다. | 필요 - ADR-011: 검색 동기화 지연 허용치와 재처리 방식을 결정 |
| Day 3: 재고 변경 원장 모델을 설계한다. | 현재는 상품 수량 컬럼이 최종 상태만 가진다. 주문, 취소, 복구, 관리자 조정이 늘어나면 어떤 이벤트가 재고를 바꿨는지 추적하기 어렵다. | 원장은 감사와 CS에 강하지만 쓰기 경로가 길어지고 데이터가 빠르게 증가한다. 모든 변경을 기록할지 핵심 변경부터 기록할지 선택해야 한다. | 필요 - ADR-012: 재고 원장의 기록 범위와 보관 기간을 결정 |
| Day 4: 부분 취소·부분 환불의 주문 라인 상태를 설계한다. | 실제 이커머스에서는 일부 품절, 일부 배송, 일부 반품이 자주 발생한다. 주문 전체 상태만으로는 라인별 취소와 환불 가능 여부를 정확히 표현하기 어렵다. | 라인 상태가 늘어나면 주문 상태 계산이 복잡해진다. 대신 고객 응대와 정산 정확도가 올라간다. | 필요 - ADR-013: 주문 전체 상태와 주문 라인 상태의 책임 분리를 결정 |
| Day 5: 쿠폰 할인 배분과 부분 환불 금액 계산 규칙을 정한다. | 쿠폰이 적용된 주문에서 일부 상품만 환불하면 할인 금액을 어떻게 나눌지 결정해야 한다. 규칙이 없으면 환불 금액이 케이스마다 달라져 CS와 정산 리스크가 생긴다. | 비례 배분은 일관적이지만 고객 체감과 다를 수 있고, 특정 상품 우선 배분은 정책 설명이 어려울 수 있다. | 필요 - ADR-013: 쿠폰 할인 배분 방식과 반올림 기준을 결정 |
| Day 6: 모듈러 모놀리식 공개 API 경계 규칙을 정한다. | 현재는 서비스 간 DTO 호출 중심이라 내부 엔티티 침범이 심하다고 보기는 어렵다. 다만 도메인이 커질수록 다른 모듈의 내부 모델에 의존하지 않도록 공개 서비스/API 경계를 정해야 한다. | 경계가 엄격해지면 단순 호출보다 DTO와 변환 코드가 늘어난다. 대신 변경 영향 범위가 줄고 추후 확장 판단이 쉬워진다. | 필요 - ADR-014: 모듈 간 허용 의존성과 공개 API 경계를 결정 |
| Day 7: SLO와 알림 초기 기준안을 만든다. | 평균 응답 시간보다 주문 생성 실패율, 결제 실패율, 결제-주문 불일치 건수, 재고 차감 실패율이 운영 판단에 더 직접적이다. 초기 기준안으로 주문 생성 p95 500ms 초과, 결제 요청 p95 1s 초과, 결제 불일치 1건 이상 발생 시 알림을 검토한다. | 알림 기준이 낮으면 피로도가 높고, 높으면 장애 감지가 늦다. 처음에는 보수적으로 관찰용 대시보드부터 만들고 알림을 단계적으로 켜는 편이 낫다. | 필요 - ADR-015: SLO 지표와 알림 임계치를 결정 |
