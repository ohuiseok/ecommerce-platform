# ADR-013: 부분 취소·부분 환불 상태 모델

## 상태

Accepted

## 배경

현재 주문은 `orders.status`의 전체 주문 상태와 `order_items`의 상품, 수량, 단가만 가진다. 주문 생성, 결제 확정, 배송 진행, 전체 취소는 ADR-001의 주문 상태 전이표로 제어한다.

하지만 실제 이커머스에서는 주문 안의 일부 상품만 품절되거나, 일부 상품만 출고 전 취소되거나, 배송 완료 후 일부 상품만 반품·환불되는 일이 자주 발생한다. 이 상황을 주문 전체 상태만으로 표현하면 정상 배송 중인 라인과 취소·환불된 라인을 구분하기 어렵고, 재고 복구, 환불 가능 여부, CS 안내, 정산 기준이 모두 불명확해진다.

따라서 주문 전체 상태는 주문 헤더의 큰 진행 단계를 나타내고, 상품별 취소·반품·환불 가능 여부는 주문 라인 상태가 담당하도록 책임을 분리한다.

## 결정

부분 취소와 부분 환불은 주문 전체 상태를 새 enum으로 계속 늘리는 방식이 아니라 `order_items`에 라인 상태를 추가해 표현한다. 주문 전체 상태는 결제와 배송의 대표 진행 상태를 유지하고, 각 주문 라인은 취소·반품·환불의 세부 생명주기를 가진다.

| 항목 | 결정 |
| --- | --- |
| 주문 전체 상태 역할 | 주문 헤더의 결제·배송 대표 진행 상태 |
| 주문 라인 상태 역할 | 상품 단위 취소, 출고, 배송 완료, 반품, 환불 진행 상태 |
| 부분 취소 단위 | `order_item_id` 기준 전체 수량 취소를 먼저 지원 |
| 부분 수량 취소 | 같은 상품 라인을 취소 수량과 유지 수량으로 분리하는 기능을 별도 단계에서 검토 |
| 환불 금액 기준 | 라인별 결제 금액과 할인 배분 금액을 기반으로 계산 |
| 쿠폰 할인 배분 | 다음 작업에서 ADR-013에 별도 섹션으로 확장 |
| 재고 복구 기준 | 취소 또는 반품 확정 라인만 복구 |
| 주문 전체 취소 | 모든 라인이 취소되면 기존 `orders.status = CANCELLED`로 전이 |

초기 구현은 부분 수량 취소보다 라인 전체 취소를 우선한다. 예를 들어 한 주문 라인이 상품 A 3개라면 3개 전체를 취소하거나 유지한다. 1개만 취소해야 하는 요구가 생기면 원 라인을 2개 유지 라인과 1개 취소 라인으로 분리하는 정책을 추가로 설계한다.

## 주문 라인 상태

`order_items`에 `status` 컬럼을 추가하고 아래 상태를 사용한다.

| 상태 | 의미 | 다음 상태 |
| --- | --- | --- |
| `ORDERED` | 주문 생성 후 결제 대기 또는 결제 확정 전 라인 | `CONFIRMED`, `CANCELLED` |
| `CONFIRMED` | 결제 확정 후 출고 준비 전 라인 | `PREPARING`, `CANCELLED` |
| `PREPARING` | 출고 준비 중인 라인 | `SHIPPED`, `CANCELLED` |
| `SHIPPED` | 배송 중인 라인 | `DELIVERED` |
| `DELIVERED` | 배송 완료된 라인 | `RETURN_REQUESTED`, `REFUND_REQUESTED` |
| `CANCELLED` | 출고 전 취소 완료 라인 | 없음 |
| `RETURN_REQUESTED` | 배송 후 반품 접수 라인 | `RETURNED`, `RETURN_REJECTED` |
| `RETURN_REJECTED` | 반품 거부 라인 | 없음 |
| `RETURNED` | 반품 입고 확인 라인 | `REFUND_REQUESTED` |
| `REFUND_REQUESTED` | 환불 요청 또는 환불 처리 대기 라인 | `REFUNDED`, `REFUND_FAILED` |
| `REFUND_FAILED` | 환불 실패로 운영 보정이 필요한 라인 | `REFUND_REQUESTED` |
| `REFUNDED` | 환불 완료 라인 | 없음 |

`CANCELLED`, `RETURN_REJECTED`, `REFUNDED`는 라인 기준 종결 상태다. `REFUND_FAILED`는 PG 장애나 정산 오류 후 재시도할 수 있도록 종결 상태로 보지 않는다.

## 주문 전체 상태와 라인 상태의 관계

주문 전체 상태는 라인 상태를 집계해 보조적으로 갱신할 수 있지만, 모든 라인 상태를 주문 전체 상태 하나에 압축하지 않는다.

| 상황 | 주문 전체 상태 정책 |
| --- | --- |
| 모든 라인이 `ORDERED` | `PENDING` 유지 |
| 결제 성공 후 하나 이상의 라인이 `CONFIRMED` 이상 | `CONFIRMED` 또는 이후 배송 상태 유지 |
| 일부 라인만 `CANCELLED` | 주문 전체 상태는 유지하고 취소 라인만 제외 |
| 모든 라인이 `CANCELLED` | `CANCELLED`로 전이 |
| 일부 라인이 `SHIPPED` 또는 `DELIVERED` | 주문 전체 상태는 가장 진행된 배송 상태를 대표값으로 사용 |
| 일부 라인이 `RETURN_REQUESTED` 이상 | 주문 전체 상태는 `DELIVERED`를 유지하고 환불·반품은 라인 상태로 표현 |
| 모든 라인이 `REFUNDED` | 주문 전체 상태에 새 환불 완료 상태를 추가하지 않고 라인 상태로 판단 |

주문 전체 상태는 사용자 목록, 운영자 필터, 결제·배송의 대표 단계에 적합한 값으로 유지한다. CS나 정산, 환불 가능 여부 판단은 반드시 라인 상태를 함께 조회한다.

## 취소와 환불 정책

출고 전 취소와 배송 후 환불은 서로 다른 흐름으로 처리한다.

| 업무 | 허용 라인 상태 | 처리 |
| --- | --- | --- |
| 출고 전 부분 취소 | `ORDERED`, `CONFIRMED`, `PREPARING` | 라인을 `CANCELLED`로 바꾸고 재고를 복구한다. |
| 배송 중 취소 | `SHIPPED` | 취소하지 않고 반품 흐름으로 안내한다. |
| 배송 후 반품 접수 | `DELIVERED` | 라인을 `RETURN_REQUESTED`로 바꾼다. |
| 반품 입고 확정 | `RETURN_REQUESTED` | 라인을 `RETURNED`로 바꾸고 재고 복구 가능 여부를 판단한다. |
| 환불 요청 | `DELIVERED`, `RETURNED` | 라인을 `REFUND_REQUESTED`로 바꾸고 결제 환불을 요청한다. |
| 환불 성공 | `REFUND_REQUESTED` | 라인을 `REFUNDED`로 바꾼다. |
| 환불 실패 | `REFUND_REQUESTED` | 라인을 `REFUND_FAILED`로 바꾸고 운영 보정 대상으로 등록한다. |

재고 복구는 출고 전 취소와 재판매 가능한 반품 입고 확정에서만 수행한다. 환불 성공 자체가 항상 재고 복구를 의미하지 않는다. 파손, 사용 흔적, 판매 불가 반품은 환불은 가능하지만 재고에 더하지 않을 수 있다.

## 데이터 모델 변경 방향

초기 구현 시 `order_items`에는 아래 필드를 추가한다.

| 필드 | 정책 |
| --- | --- |
| `status` | 라인 상태, 기본값 `ORDERED`, not null |
| `cancelled_at` | 출고 전 취소 완료 시각 |
| `return_requested_at` | 반품 접수 시각 |
| `returned_at` | 반품 입고 확인 시각 |
| `refund_requested_at` | 환불 요청 시각 |
| `refunded_at` | 환불 완료 시각 |
| `refund_failure_reason` | 환불 실패 또는 운영 보정 사유 |

금액 필드는 다음 작업의 쿠폰 할인 배분 정책에서 확정한다. 다만 라인별 환불을 안정적으로 계산하려면 최소한 라인 원금, 라인 할인액, 라인 결제 금액을 저장하거나 재현 가능하게 만들어야 한다.

## Idempotency와 감사

부분 취소와 부분 환불은 사용자가 재시도하거나 운영자가 같은 요청을 다시 처리할 수 있으므로 업무 요청 단위 idempotency key를 둔다.

| 업무 | idempotency key 예시 |
| --- | --- |
| 부분 취소 | `ORDER_ITEM_CANCEL:{orderId}:{orderItemId}:{requestId}` |
| 반품 접수 | `RETURN_REQUEST:{orderId}:{orderItemId}:{requestId}` |
| 환불 요청 | `REFUND_REQUEST:{orderId}:{orderItemId}:{requestId}` |
| 환불 성공 반영 | `REFUND_COMPLETED:{paymentTransactionId}:{orderItemId}` |

상태 변경, 재고 복구, 환불 요청 기록, Outbox 이벤트 저장은 같은 로컬 트랜잭션 안에서 처리한다. 실제 PG 환불 호출은 결제 idempotency 정책을 따르고, 성공·실패 결과 반영은 웹훅 idempotency 정책과 운영 보정 목록을 함께 사용한다.

## 적용 범위

- 현재 단계에서는 코드와 테이블을 변경하지 않고 상태 모델만 확정한다.
- ADR-001의 주문 전체 상태 전이 정책은 유지한다.
- 주문 라인 상태 추가 후에는 주문 취소, 만료 주문 복구, 결제 실패 복구가 라인 상태도 함께 갱신해야 한다.
- 부분 수량 취소, 교환, 배송 묶음 분리, 다중 운송장 처리는 별도 설계 대상으로 둔다.
- 쿠폰 할인 배분과 부분 환불 금액 계산 규칙은 다음 작업에서 이 ADR을 확장해 결정한다.

## 결과

부분 취소와 부분 환불은 주문 전체 상태가 아니라 주문 라인 상태로 표현한다. 주문 전체 상태는 결제와 배송의 대표 진행 상태로 유지하고, 라인 상태는 상품 단위 취소, 반품, 환불 가능 여부와 정산 기준을 담당한다.

이 결정은 기존 주문 상태 머신을 과도하게 복잡하게 만들지 않으면서도, 실제 이커머스 운영에서 필요한 부분 취소·부분 환불 흐름을 안전하게 확장할 기준을 제공한다.
