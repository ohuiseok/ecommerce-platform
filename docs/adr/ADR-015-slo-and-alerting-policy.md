# ADR-015: SLO 지표와 알림 초기 기준

## 상태

Accepted

## 배경

현재 애플리케이션은 주문 생성, 결제 요청, 쿠폰 사용, 재고 차감, Outbox 발행, PG 웹훅 반영처럼 장애 영향이 큰 흐름을 포함한다. Phase 1과 Phase 2에서는 상태 전이, idempotency, 조건부 업데이트, 웹훅 중복 처리, Outbox retry 같은 안정성 장치를 추가했다.

하지만 안정성 장치가 있어도 운영자가 언제 문제로 판단하고 개입할지 기준이 없으면 장애 감지가 늦거나, 반대로 일시적인 지연마다 알림이 발생해 알림 피로가 커질 수 있다. 특히 평균 응답 시간만 보면 일부 사용자가 겪는 주문 실패, 결제 불일치, 재고 차감 실패 같은 위험을 놓칠 수 있다.

따라서 초기 SLO는 사용자 구매 흐름과 데이터 일관성에 직접 연결되는 지표를 우선한다. 대시보드는 관찰용으로 먼저 만들고, 알림은 명확한 사용자 영향이나 운영 개입이 필요한 상태부터 단계적으로 켠다.

## 결정

초기 SLO는 주문, 결제, 데이터 일관성, 비동기 발행 네 영역으로 나눈다. 평균값보다 p95 지연, 실패율, 불일치 건수, dead-letter 발생처럼 운영 판단에 직접 쓰이는 지표를 우선 수집한다.

| 영역 | 초기 SLO 또는 관찰 기준 | 알림 기준 |
| --- | --- | --- |
| 주문 생성 | p95 500ms 이하 | 10분 동안 p95 500ms 초과 또는 실패율 1% 초과 |
| 결제 요청 | p95 1s 이하 | 10분 동안 p95 1s 초과 또는 PG 통신 실패율 3% 초과 |
| 결제-주문 일관성 | 불일치 0건 | 불일치 1건 이상 |
| 재고 차감 | 초과 판매 0건 | 재고 음수 또는 초과 판매 의심 1건 이상 |
| 쿠폰 사용 | 동일 사용자 쿠폰 중복 사용 0건 | 중복 사용 의심 1건 이상 |
| Outbox 발행 | 발행 지연 p95 1분 이하 | dead-letter 1건 이상 또는 발행 지연 p95 5분 초과 |
| 웹훅 처리 | 중복 이벤트 idempotent 처리 | 처리 실패율 1% 초과 또는 미처리 이벤트 5분 이상 적체 |

알림은 처음부터 모든 경고를 강하게 울리지 않는다. 주문 생성 실패율, 결제-주문 불일치, 재고 음수, Outbox dead-letter처럼 사용자 피해나 운영 보정이 필요한 신호는 즉시 알림 대상으로 둔다. 단순 p95 지연 초과는 초기에는 관찰 알림으로 시작하고, 반복 패턴이 확인되면 호출 알림으로 승격한다.

## 핵심 지표

구매 흐름의 정상 여부를 판단하기 위해 아래 지표를 우선 수집한다.

| 지표 | 설명 | 라벨 |
| --- | --- | --- |
| `http.server.requests` | API별 응답 시간과 상태 코드 | `uri`, `method`, `status` |
| `order.create.duration` | 주문 생성 유스케이스 처리 시간 | `result`, `failure_reason` |
| `order.create.failures` | 주문 생성 실패 건수 | `failure_reason` |
| `payment.request.duration` | 결제 요청 처리 시간 | `result`, `pg_result` |
| `payment.request.failures` | 결제 요청 실패 건수 | `failure_reason` |
| `payment.order.mismatch.count` | 결제와 주문 상태 불일치 건수 | `mismatch_type` |
| `inventory.decrease.failures` | 재고 차감 실패 건수 | `reason` |
| `coupon.use.failures` | 쿠폰 사용 실패 건수 | `reason` |
| `outbox.publish.lag` | Outbox 이벤트 생성부터 발행 성공까지 걸린 시간 | `event_type` |
| `outbox.dead_letter.count` | dead-letter 상태 이벤트 건수 | `event_type` |
| `webhook.processing.failures` | 웹훅 처리 실패 건수 | `event_type`, `failure_reason` |

사용자 ID, 배송지, 카드번호, 전화번호 같은 개인정보는 지표 라벨에 넣지 않는다. 주문 ID, 결제 ID, 사용자 ID는 로그와 trace에서 필요한 범위로만 사용하고 ADR-003의 마스킹 기준을 따른다.

## 알림 등급

초기 알림은 세 단계로 운영한다.

| 등급 | 의미 | 예시 |
| --- | --- | --- |
| `P1` | 즉시 사용자 피해 또는 금전·재고 불일치 가능성이 있다. | 결제-주문 불일치 1건 이상, 재고 음수, Outbox dead-letter 발생 |
| `P2` | 구매 흐름 품질 저하가 지속되고 있다. | 주문 생성 실패율 1% 초과, 결제 요청 p95 1s 초과, PG 실패율 3% 초과 |
| `P3` | 추세 관찰과 개선 작업 후보로 본다. | 검색 또는 목록 지연 증가, Outbox 발행 지연 p95 1분 초과 |

`P1`은 운영자가 즉시 확인해야 하는 알림이다. `P2`는 10분 이상 지속될 때 알림을 보내고, 자연 회복되더라도 사후 분석 대상에 남긴다. `P3`는 대시보드와 근무 시간 알림으로 시작한다.

## 대시보드 구성

초기 대시보드는 평균보다 분포와 오류 원인을 확인하기 쉽게 구성한다.

- 주문 생성 요청 수, p50, p95, p99, 실패율
- 결제 요청 수, p50, p95, p99, PG 결과별 실패율
- 결제 완료 주문 중 주문 상태가 `CONFIRMED`가 아닌 건수
- 주문은 `CONFIRMED`인데 완료 결제가 없는 건수
- 재고 차감 실패 건수와 상품별 상위 실패 사유
- 쿠폰 사용 실패 건수와 중복 사용 의심 건수
- Outbox 상태별 이벤트 수, 발행 지연, dead-letter 건수
- 웹훅 수신 수, 중복 이벤트 수, 처리 실패 수

대시보드는 도메인별 세부 화면보다 구매 흐름 전체를 한눈에 보는 화면을 먼저 만든다. 사용자가 상품을 선택해 주문하고 결제 완료에 도달하는 경로에서 어디가 막히는지 빠르게 파악하는 것이 우선이다.

## 알림 기준

초기 알림 기준은 보수적으로 시작한다.

| 알림 | 조건 | 등급 |
| --- | --- | --- |
| 주문 생성 지연 | 10분 동안 `order.create.duration` p95 500ms 초과 | P2 |
| 주문 생성 실패율 | 10분 동안 주문 생성 실패율 1% 초과 | P2 |
| 결제 요청 지연 | 10분 동안 `payment.request.duration` p95 1s 초과 | P2 |
| PG 실패율 증가 | 10분 동안 PG 통신 실패율 3% 초과 | P2 |
| 결제-주문 불일치 | 불일치 조회 결과 1건 이상 | P1 |
| 재고 음수 또는 초과 판매 | 음수 재고 또는 초과 판매 의심 1건 이상 | P1 |
| 쿠폰 중복 사용 의심 | 같은 사용자 쿠폰이 둘 이상의 주문에 사용된 정황 1건 이상 | P1 |
| Outbox dead-letter | dead-letter 이벤트 1건 이상 | P1 |
| Outbox 발행 지연 | 10분 동안 발행 지연 p95 5분 초과 | P2 |
| 웹훅 처리 실패 | 10분 동안 처리 실패율 1% 초과 | P2 |

알림 기준은 운영 데이터가 쌓이면 재조정한다. 초기 값은 장애를 놓치지 않기 위한 기준이며, 실제 트래픽과 실패 패턴이 확인되면 업무 영향도에 맞게 임계치를 조정한다.

## 오류 예산

초기 오류 예산은 엄격한 월간 계약보다 관찰과 개선 우선순위를 정하기 위한 기준으로 사용한다.

| 흐름 | 월간 목표 |
| --- | --- |
| 주문 생성 성공률 | 99.5% 이상 |
| 결제 요청 내부 처리 성공률 | 99.0% 이상 |
| 결제-주문 불일치 | 0건 |
| 재고 초과 판매 | 0건 |
| Outbox dead-letter 미처리 | 0건 |

PG 자체 승인 거절, 카드 한도 초과, 고객 입력 오류처럼 정상적인 업무 실패는 내부 가용성 실패율에서 제외한다. 반면 PG 타임아웃, DB 오류, idempotency 충돌 처리 실패, 상태 전이 오류는 내부 실패로 계산한다.

## 적용 범위

- 현재 단계에서는 SLO와 알림 기준을 문서로 정의한다.
- 지표 수집 라이브러리, 대시보드, 알림 채널 연동은 별도 구현 작업으로 분리한다.
- 개인정보를 지표 라벨에 넣지 않는다.
- traceId와 로그 필드는 ADR-003을 따른다.
- 결제-주문 불일치 조회는 Phase 1 Day 7에서 추가한 운영 조회 기준을 활용한다.
- Outbox retry와 dead-letter 기준은 ADR-007을 따른다.

## 결과

이 애플리케이션은 주문 생성, 결제 요청, 결제-주문 일관성, 재고, 쿠폰, Outbox, 웹훅을 중심으로 초기 SLO와 알림 기준을 가진다. 모든 지표를 한 번에 강한 알림으로 전환하지 않고, 사용자 피해와 운영 보정이 필요한 신호부터 우선 알림 대상으로 둔다.

이 결정은 평균 응답 시간만으로는 드러나지 않는 구매 흐름 장애와 데이터 불일치를 더 빠르게 발견하고, 향후 대시보드와 알림 구현의 기준선을 제공한다.
