# ADR-010: 상품 상세 캐시 필드 범위와 무효화 정책

## 상태

Accepted

## 배경

상품 상세 조회는 `ProductService.getProduct`에서 단일 상품을 `productId`로 조회한 뒤 `ProductResponse.ProductInfo`로 변환한다. 상세 화면은 목록보다 사용자가 구매 여부를 판단하는 정보가 많고, 인기 상품은 같은 상품 ID에 대한 반복 조회가 자주 발생할 수 있다.

반면 현재 상품 상세 응답에는 상품명, 설명, 가격, 이미지, 판매 상태뿐 아니라 `stockQuantity`, `averageRating`, `reviewCount`처럼 자주 바뀌거나 신선도가 중요한 값도 함께 포함된다. 주문 생성은 DB 조건부 업데이트로 최종 재고를 검증하지만, 상세 화면에 오래된 재고를 보여주면 사용자 경험이 나빠지고 품절 상태를 늦게 인지할 수 있다.

따라서 상품 상세 캐시는 목록 캐시보다 key 공간은 단순하지만, 필드별 신선도와 무효화 기준을 더 엄격하게 정해야 한다.

## 결정

상품 상세 캐시는 기본 비활성 상태로 두고, 상세 조회 트래픽이나 응답 시간이 기준을 넘을 때 도입한다. 초기 캐시는 공개 상품 상세의 안정적인 표시 정보만 대상으로 하며, 재고 수량은 긴 TTL 캐시의 신뢰 대상으로 삼지 않는다.

| 항목 | 결정 |
| --- | --- |
| 도입 조건 | 상품 상세 p95 200ms 초과 또는 특정 상품 상세 조회가 짧은 시간에 반복될 때 검토 |
| 캐시 key | `product:detail:{productId}` |
| 기본 TTL | 30초 |
| 최대 TTL | 2분을 넘기지 않음 |
| 캐시 대상 상태 | `ACTIVE` 상품 상세 |
| 제외 대상 | `INACTIVE` 상품, 관리자 재고 조회, 주문 생성 검증 |
| 재고 수량 | 응답에는 포함할 수 있지만 짧은 TTL만 허용하고 주문 생성 시 DB를 최종 기준으로 둠 |
| 무효화 | 상품 수정, 가격 변경, 판매 상태 변경, 삭제, 리뷰 통계 변경 시 해당 상품 key 삭제 |

현재 단계에서는 캐시 인프라나 `@Cacheable` 구현을 추가하지 않는다. 이 ADR은 이후 상품 상세 캐시를 구현할 때 필드 범위, TTL, 무효화 기준으로 사용한다.

## 캐시 필드 범위

상세 캐시는 사용자 화면 표시를 빠르게 하기 위한 읽기 최적화다. 구매 가능 여부와 결제 가능 여부를 확정하는 source of truth로 사용하지 않는다.

| 필드 | 캐시 여부 | 정책 |
| --- | --- | --- |
| `productId` | 포함 | key와 동일한 안정 식별자다. |
| `name`, `description`, `imageUrl` | 포함 | 변경 빈도가 낮고 상세 화면 렌더링에 필요하다. |
| `category`, `brand` | 포함 | 탐색과 표시 정보로 사용한다. |
| `price` | 포함 | 가격 변경 시 즉시 무효화한다. |
| `status` | 포함 | `ACTIVE`만 캐시하고 상태 변경 시 즉시 무효화한다. |
| `averageRating`, `reviewCount` | 포함 | 리뷰 작성 후 통계 변경 시 무효화한다. |
| `stockQuantity` | 제한적 포함 | 짧은 TTL에서만 표시용으로 사용하며, 주문 생성과 재고 차감 판단에는 사용하지 않는다. |
| `createdAt`, `updatedAt` | 포함 | 표시와 디버깅 보조 정보로 사용한다. |

재고 신선도가 중요한 화면에서는 상세 캐시 값만 믿지 않고 `checkStock` 또는 주문 생성 시점의 조건부 재고 차감을 기준으로 한다. 재고 수량을 상세 응답에서 제거하거나 별도 stock endpoint로 분리하는 결정은 API 호환성 변경이 필요하므로 별도 작업으로 다룬다.

## TTL 정책

기본 TTL은 30초로 둔다. 인기 상품의 반복 상세 조회를 완화하되, 가격과 재고, 리뷰 통계 변경이 오래 지연되지 않도록 최대 TTL은 2분을 넘기지 않는다.

TTL은 아래 원칙을 따른다.

- 구매 전환에 직접 영향을 주는 가격과 판매 상태는 이벤트 기반 무효화를 우선한다.
- 재고는 주문마다 바뀔 수 있으므로 긴 TTL 최적화 대상으로 보지 않는다.
- 이미지나 설명처럼 안정적인 필드만 별도 장기 캐시하는 최적화는 CDN 또는 정적 자산 정책에서 다룬다.
- 개인화 가격, 사용자별 쿠폰, 찜 여부가 상세 응답에 추가되면 해당 응답은 공용 상세 캐시 대상에서 제외하거나 개인화 필드를 별도 조회로 분리한다.

## 무효화 정책

상품 상세 캐시는 상품 단위 key 하나를 삭제하면 되므로 목록 캐시보다 무효화 범위가 단순하다. 아래 변경이 성공적으로 커밋된 뒤 해당 상품의 `product:detail:{productId}` key를 삭제한다.

- 상품명, 설명, 이미지, 카테고리, 브랜드 변경
- 가격 변경
- 판매 상태 변경
- 상품 삭제 또는 비활성화
- 재고 수량 관리자 변경
- 주문 생성, 주문 취소, 만료 주문 복구로 인한 재고 변경
- 리뷰 작성, 수정, 삭제로 인한 `averageRating`, `reviewCount` 변경

주문 생성과 취소는 빈번하므로 모든 재고 변경마다 상세 캐시를 삭제하면 캐시 효율이 낮아질 수 있다. 초기 구현은 정확성을 우선해 삭제 방식을 택하고, 트래픽이 커지면 재고 필드를 캐시 응답에서 분리하거나 더 짧은 stock-only 캐시를 별도로 검토한다.

## 적용 범위

- 상품 상세 캐시 key는 `productId`만 사용한다.
- 사용자 ID, traceId, 요청 시각처럼 상세 결과에 영향을 주지 않는 값은 key에 포함하지 않는다.
- 캐시 hit 여부와 관계없이 주문 생성은 `ProductRepository.decreaseStockIfAvailable`의 DB 조건부 업데이트를 최종 검증으로 사용한다.
- 상품 목록 캐시는 ADR-009의 key, TTL, 무효화 정책을 따른다.
- 검색 read model 도입 여부는 ADR-011에서 별도로 결정한다.
- 다중 인스턴스 배포에서 상세 캐시를 도입하면 로컬 캐시보다 Redis 같은 공유 캐시를 우선 검토한다.

## 결과

상품 상세 캐시는 단일 상품 ID 기반으로 제한적으로 도입한다. TTL은 기본 30초로 짧게 유지하고, 가격, 판매 상태, 상품 정보, 리뷰 통계, 재고 변경 시 상품 단위 key를 무효화한다.

이 결정은 인기 상품 상세 조회의 반복 DB 접근을 줄일 수 있는 기준을 제공하면서도, 주문 생성과 재고 차감의 최종 판단은 DB 조건부 업데이트에 남겨 재고 불일치 위험을 낮춘다.
