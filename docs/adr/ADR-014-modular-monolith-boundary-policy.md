# ADR-014: 모듈러 모놀리식 도메인 경계와 공개 API 규칙

## 상태

Accepted

## 배경

현재 애플리케이션은 하나의 Spring Boot 모놀리식 안에서 `user`, `product`, `cart`, `order`, `payment`, `coupon`, `review`, `outbox` 패키지로 도메인을 나눈다. 각 도메인은 대체로 `controller`, `dto`, `service`, `repository`, `entity` 하위 패키지를 가진다.

서비스 분리는 현재 목표가 아니다. 같은 DB와 같은 배포 단위를 유지하면서도 도메인 경계를 명확히 해야 주문, 결제, 쿠폰, 재고, 리뷰 기능이 커질 때 변경 영향 범위를 통제할 수 있다. 특히 주문은 사용자, 상품, 장바구니, 쿠폰, 결제와 연결되는 중심 도메인이므로 다른 모듈의 내부 엔티티나 리포지토리에 직접 의존하기 시작하면 상태 전이, 트랜잭션, 보정 정책이 흩어질 위험이 크다.

현재 코드에는 서비스 간 직접 호출이 존재한다. 예를 들어 주문 서비스는 사용자, 상품, 장바구니, 쿠폰 서비스를 호출하고, 결제 서비스는 주문 서비스를 호출한다. 이 구조는 모놀리식 안에서는 단순하고 테스트하기 쉽지만, 호출 대상 모듈의 엔티티와 리포지토리까지 자유롭게 접근하도록 허용하면 모듈 경계가 사실상 사라진다.

따라서 모듈러 모놀리식으로 유지하기 위한 공개 API와 내부 구현의 경계를 먼저 정한다.

## 결정

도메인 간 동기 협업은 같은 프로세스 안의 공개 애플리케이션 서비스 또는 공개 조회 DTO를 통해 수행한다. 다른 도메인의 `repository`와 `entity`는 기본적으로 내부 구현으로 보고 직접 접근하지 않는다.

| 항목 | 결정 |
| --- | --- |
| 배포 단위 | 단일 Spring Boot 애플리케이션 유지 |
| 데이터베이스 | 단일 DB 유지, 도메인별 테이블 소유권만 논리적으로 구분 |
| 공개 진입점 | 각 도메인의 `service` 패키지 중 공개 유스케이스 메서드 |
| 공개 데이터 | 요청·응답 DTO, 식별자, 값 객체 성격의 enum |
| 내부 구현 | `entity`, `repository`, 도메인 내부 보정 로직 |
| 교차 쓰기 | 소유 도메인의 서비스 메서드로만 수행 |
| 교차 조회 | 공개 조회 서비스 또는 DTO 반환 메서드로 수행 |
| 비동기 연동 | Outbox 이벤트와 소비자 idempotency 정책 사용 |

현재 패키지 구조를 바로 대규모 변경하지는 않는다. 대신 새 기능과 리팩터링부터 아래 의존성 규칙을 적용하고, 기존 위반은 기능 변경이 닿는 범위에서 점진적으로 줄인다.

## 모듈 소유권

각 도메인은 자기 테이블과 상태 전이 규칙을 소유한다.

| 모듈 | 소유 데이터와 책임 | 외부에 제공할 공개 기능 |
| --- | --- | --- |
| `user` | 사용자, 인증에 필요한 사용자 정보 | 사용자 존재 확인, 사용자 조회 DTO, 인증 토큰 발급 |
| `product` | 상품, 카테고리, 판매 상태, 재고 수량 | 상품 조회, 가격 검증, 조건부 재고 차감·복구 |
| `cart` | 장바구니와 장바구니 라인 | 장바구니 조회, 추가, 수정, 비우기 |
| `order` | 주문, 주문 라인, 배송지, 주문 상태 전이 | 주문 생성, 취소, 만료 복구, 상태 변경 |
| `payment` | 결제, 웹훅, 보정 작업 | 결제 요청, 결제 취소, 웹훅 반영, 불일치 조회 |
| `coupon` | 쿠폰, 사용자 쿠폰, 쿠폰 사용 상태 | 할인 계산, 쿠폰 사용, 쿠폰 복구, 발급 |
| `review` | 리뷰와 평점 | 리뷰 작성, 수정, 조회 |
| `outbox` | 이벤트 저장과 발행 상태 | 이벤트 저장, 발행 대상 조회, 성공·실패 반영 |

테이블을 소유한 모듈만 해당 엔티티의 상태를 직접 변경한다. 다른 모듈은 식별자와 공개 메서드를 통해 요청한다. 예를 들어 주문 생성이 상품 재고를 차감해야 할 때 `ProductRepository`를 직접 호출하지 않고 상품 모듈의 공개 서비스가 제공하는 조건부 차감 기능을 사용한다.

## 허용 의존성

도메인 간 의존성은 아래 방향만 허용한다.

| 호출 형태 | 허용 여부 | 정책 |
| --- | --- | --- |
| `order.service` -> `product.service` | 허용 | 주문 생성에 필요한 상품 조회와 재고 차감은 상품 공개 서비스로 수행한다. |
| `order.service` -> `coupon.service` | 허용 | 할인 계산과 쿠폰 사용·복구는 쿠폰 공개 서비스로 수행한다. |
| `order.service` -> `cart.service` | 허용 | 장바구니 주문 생성 시 공개 DTO로 장바구니 내용을 읽는다. |
| `payment.service` -> `order.service` | 허용 | 결제 성공·실패에 따른 주문 상태 변경은 주문 공개 서비스로 요청한다. |
| `review.service` -> `order.service`, `product.service`, `user.service` | 허용 | 구매 검증과 표시 정보 조회는 공개 조회 메서드로 수행한다. |
| 임의 모듈 -> 다른 모듈의 `repository` | 금지 | 테이블 소유권과 트랜잭션 규칙을 우회하므로 허용하지 않는다. |
| 임의 모듈 -> 다른 모듈의 `entity` 상태 변경 | 금지 | 상태 전이와 불변식을 우회하므로 허용하지 않는다. |
| 임의 모듈 -> 다른 모듈의 DTO | 허용 | 공개 API 계약으로 쓰는 DTO만 허용한다. |
| `outbox.service` -> 도메인 엔티티 | 제한 허용 | 이벤트 payload 생성에 필요한 읽기 전용 참조만 허용하고 상태 변경은 하지 않는다. |

같은 모듈 안에서는 엔티티와 리포지토리를 자유롭게 사용할 수 있다. 테스트 코드에서는 통합 테스트 데이터 준비를 위해 리포지토리를 사용할 수 있지만, 운영 코드의 의존성 규칙을 흐리는 방식으로 헬퍼를 만들지 않는다.

## 공개 API 규칙

도메인 공개 서비스는 다른 모듈이 알아야 하는 유스케이스 단위 메서드만 노출한다.

| 규칙 | 설명 |
| --- | --- |
| 유스케이스 이름 사용 | `decreaseStock`, `markOrderConfirmed`, `restoreCoupon`처럼 업무 의미가 드러나는 이름을 사용한다. |
| 내부 엔티티 반환 금지 | 다른 모듈 호출자에게 JPA 엔티티를 그대로 반환하지 않는다. 필요한 필드는 DTO로 반환한다. |
| 리포지토리 노출 금지 | 다른 모듈이 소유 테이블을 직접 조회·수정하지 않도록 repository는 내부 구현으로 둔다. |
| 상태 변경은 소유 모듈에서 검증 | 주문 상태 전이, 쿠폰 상태 전이, 결제 상태 전이는 각각 소유 모듈이 검증한다. |
| 트랜잭션 경계 명시 | 한 유스케이스에서 여러 모듈을 호출하는 오케스트레이션 서비스가 트랜잭션 경계를 가진다. |
| 외부 I/O 분리 | PG 호출 같은 외부 I/O는 DB 트랜잭션 안에서 최소화하고, 실패 복구와 idempotency 정책을 함께 둔다. |

기존 코드에서 일부 DTO가 엔티티를 변환하는 정적 팩토리를 가지고 있는 것은 유지할 수 있다. 다만 그 DTO가 다른 모듈의 쓰기 로직에 엔티티를 노출하는 통로가 되어서는 안 된다.

## 트랜잭션과 일관성

모놀리식 내부의 강한 일관성이 필요한 작업은 하나의 로컬 트랜잭션으로 처리한다. 주문 생성처럼 사용자 확인, 상품 재고 차감, 쿠폰 사용, 주문 저장이 함께 성공하거나 실패해야 하는 흐름은 주문 애플리케이션 서비스가 오케스트레이션한다.

반면 알림, 검색 색인, 정산 후속 처리처럼 핵심 저장 결과 이후에 실행돼도 되는 작업은 Outbox 이벤트로 분리한다. 이벤트 저장은 핵심 상태 변경과 같은 트랜잭션에 포함하고, 발행과 소비는 ADR-007의 retry, dead-letter, 소비자 idempotency 정책을 따른다.

도메인 간 직접 DB 조인은 운영 조회나 리포팅에서만 제한적으로 허용한다. 쓰기 유스케이스의 불변식 검증을 위해 다른 모듈 테이블을 임의로 갱신하는 조인은 금지한다.

## 패키지 구조 방향

현재 패키지 구조는 유지하되, 새 기능부터 아래 구조를 지향한다.

| 패키지 | 역할 |
| --- | --- |
| `*.controller` | HTTP 요청과 응답 매핑 |
| `*.dto` | 외부 API와 모듈 간 공개 데이터 계약 |
| `*.service` | 공개 유스케이스와 내부 오케스트레이션 |
| `*.entity` | 해당 도메인 내부 영속 모델과 상태 전이 |
| `*.repository` | 해당 도메인 내부 DB 접근 |

규모가 더 커지면 `*.api` 또는 `*.application` 패키지를 별도로 만들어 공개 서비스 인터페이스와 내부 구현을 분리할 수 있다. 하지만 현재 단계에서는 패키지 이동보다 의존성 규칙과 리뷰 기준을 먼저 적용한다.

## 예외와 점진적 개선

기존 코드의 모든 의존성을 즉시 바꾸지는 않는다. 아래 경우에는 제한적으로 예외를 허용한다.

- 오래된 코드가 이미 다른 모듈의 DTO나 엔티티를 읽기 전용으로 사용하고 있고, 즉시 위험이 낮은 경우
- 통합 테스트 데이터 준비를 위해 리포지토리를 직접 사용하는 경우
- 운영 조회나 보정 목록처럼 여러 도메인의 상태를 조합해 읽기만 하는 쿼리
- Outbox payload 생성을 위해 저장 직후 엔티티 식별자와 스냅샷 값을 읽는 경우

예외가 새 기능의 기본 패턴이 되어서는 안 된다. 기존 위반을 수정할 때는 한 번에 전체 구조를 바꾸기보다 변경 대상 유스케이스의 공개 메서드와 DTO부터 만든다.

## 적용 범위

- 현재 단계에서는 코드와 패키지를 대규모로 이동하지 않는다.
- 새 기능은 다른 도메인의 repository를 직접 주입하지 않는다.
- 새 쓰기 기능은 소유 도메인의 공개 서비스 메서드를 통해 상태를 변경한다.
- 기존 교차 엔티티 반환은 기능 변경이 닿을 때 DTO 반환으로 점진 전환한다.
- 모듈 경계 검사는 추후 ArchUnit 같은 테스트로 자동화할 수 있다.
- 서비스 분리, 별도 DB 분리, 이벤트 기반 완전 비동기화는 이 ADR의 범위가 아니다.

## 결과

이 애플리케이션은 단일 배포와 단일 DB를 유지하되, 도메인별 데이터 소유권과 공개 API 경계를 명확히 한다. 다른 모듈의 내부 엔티티와 리포지토리를 직접 사용하는 대신 공개 서비스와 DTO를 통해 협업한다.

이 결정은 현재 모놀리식의 단순함을 유지하면서도, 주문·결제·쿠폰·재고·리뷰 기능이 커질 때 변경 영향 범위를 줄이고 추후 모듈 경계 테스트나 부분적인 구조 개선을 적용할 기준을 제공한다.
