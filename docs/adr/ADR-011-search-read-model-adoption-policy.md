# ADR-011: 검색 read model 도입 기준과 동기화 지연 허용치

## 상태

Accepted

## 배경

현재 상품 검색은 `ProductRepository`의 DB 조회를 기준으로 한다. 활성 상품 목록, 카테고리, 브랜드, 가격 범위 조회는 Phase 2 Day 15에서 복합 인덱스 후보를 추가했고, 상품 목록과 상세 캐시는 ADR-009, ADR-010에서 도입 기준과 신선도 정책을 정했다.

키워드 검색은 `name`, `description`, `category`, `brand`에 `LOWER(... LIKE '%keyword%')` 조건을 적용한다. 이 방식은 구현이 단순하고 데이터 정합성이 즉시 보장되지만, 상품 수가 늘거나 키워드 검색 비중이 커지면 일반 B-tree 인덱스 효과가 제한적이다. 검색 품질도 단순 부분 문자열 매칭에 머물러 오타, 형태소, 랭킹, 동의어 같은 요구를 처리하기 어렵다.

반면 OpenSearch 같은 별도 검색 read model은 검색 성능과 품질을 높일 수 있지만, 인덱스 운영 비용, 동기화 지연, 장애 복구, 재처리 흐름이 추가된다. 따라서 현재 단계에서는 DB 검색을 기본으로 유지하고, 명확한 관측 기준을 넘을 때만 검색 read model을 도입한다.

## 결정

검색 read model은 기본 비활성 상태로 둔다. DB 인덱스와 쿼리 튜닝, 제한적인 캐시 정책을 먼저 적용한 뒤에도 검색 병목이나 검색 품질 요구가 남는 경우에만 도입한다.

| 항목 | 결정 |
| --- | --- |
| 기본 검색 저장소 | 운영 DB의 `products` 테이블 |
| 도입 후보 | OpenSearch 또는 호환 검색 엔진 기반 상품 검색 read model |
| 도입 조건 | 상품 10만 건 이상, 검색 p95 300ms 초과, 검색 쿼리로 DB CPU 70% 이상이 10분 지속 중 하나 |
| 우선 튜닝 | PostgreSQL `pg_trgm` GIN 인덱스, 검색 대상 필드 축소, 필터와 키워드 검색 분리 |
| 동기화 방식 | 도입 시 Outbox 이벤트 기반 비동기 색인 |
| 지연 허용치 | 일반 상품 정보 변경은 1분 이내 반영을 목표로 함 |
| 강한 정합성 대상 | 가격, 판매 상태, 재고 차감, 주문 가능 여부는 DB를 최종 기준으로 둠 |
| 제외 범위 | 관리자 재고 조회, 주문 생성 검증, 결제 가능 여부 판단 |

초기 검색 read model은 사용자용 상품 검색 결과를 빠르게 반환하기 위한 읽기 최적화로만 사용한다. 주문 생성, 재고 차감, 가격 검증, 상품 판매 상태 검증은 계속 DB 트랜잭션과 조건부 업데이트를 최종 기준으로 둔다.

## 도입 기준

아래 조건 중 하나가 운영 또는 운영 유사 부하 테스트에서 확인되면 검색 read model 도입을 검토한다.

- 활성 상품 수가 10만 건 이상으로 증가한다.
- 키워드 검색 API의 p95 응답 시간이 300ms를 초과한다.
- 키워드 검색 쿼리로 인한 DB CPU 사용률이 70% 이상으로 10분 이상 지속된다.
- 검색 결과 랭킹, 오타 보정, 동의어, 형태소 분석처럼 DB `LIKE` 검색으로 처리하기 어려운 검색 품질 요구가 생긴다.
- 검색 트래픽이 주문, 결제, 재고 차감 같은 쓰기 트랜잭션의 DB 자원을 눈에 띄게 압박한다.

단일 느린 쿼리나 낮은 데이터 규모의 검색 지연은 먼저 실행 계획, 인덱스, 쿼리 조건을 점검한다. 특히 키워드 검색은 read model 도입 전에 PostgreSQL `pg_trgm` 기반 GIN 인덱스와 `ILIKE` 또는 similarity 검색을 우선 검토한다.

## 도입 전 튜닝 순서

검색 read model을 추가하기 전에 아래 순서로 현재 DB 검색을 개선한다.

1. `EXPLAIN (ANALYZE, BUFFERS)`로 키워드 검색의 scan 방식과 rows 제거 비율을 확인한다.
2. `name`, `description` 등 실제 검색 가치가 높은 필드와 카테고리, 브랜드 필터를 분리한다.
3. PostgreSQL `pg_trgm` 확장과 GIN 인덱스 적용 가능성을 검토한다.
4. 검색어 최소 길이, 공백 정규화, 페이지 크기 제한으로 비효율적인 검색 요청을 줄인다.
5. 위 조치 이후에도 도입 기준을 넘으면 검색 read model을 설계한다.

이 순서를 거치면 별도 검색 엔진을 성능 문제의 첫 대응책으로 도입하는 것을 피하고, 현재 모놀리식 구조 안에서 해결 가능한 병목을 먼저 제거할 수 있다.

## 검색 read model 범위

초기 read model에는 사용자 검색 결과에 필요한 필드만 포함한다.

| 필드 | 포함 여부 | 정책 |
| --- | --- | --- |
| `productId` | 포함 | DB 상품과 검색 문서를 연결하는 안정 식별자다. |
| `name`, `description` | 포함 | 키워드 검색의 핵심 대상이다. |
| `category`, `brand` | 포함 | 필터와 랭킹 보조 정보로 사용한다. |
| `price` | 포함 | 정렬과 표시용으로 사용하되 최종 가격 검증은 DB 기준이다. |
| `status` | 포함 | 사용자 검색은 `ACTIVE` 상품만 노출한다. |
| `imageUrl` | 포함 | 검색 결과 카드 표시용이다. |
| `averageRating`, `reviewCount` | 선택 포함 | 검색 랭킹이나 표시 요구가 있을 때 포함한다. |
| `stockQuantity` | 제외 또는 제한 | 재고 신선도 위험이 크므로 검색 랭킹의 강한 기준으로 사용하지 않는다. |

검색 read model은 상품 탐색 경험을 위한 projection이다. 검색 결과에서 상품을 선택한 뒤 상세 조회, 주문 생성, 결제 가능 여부 판단은 DB 기반 API에서 다시 검증한다.

## 동기화와 지연 허용치

검색 read model을 도입하면 상품 생성, 수정, 판매 상태 변경, 삭제 이벤트를 Outbox에 저장하고 비동기 워커가 검색 인덱스에 반영한다. 상품 저장과 Outbox 이벤트 저장은 같은 로컬 트랜잭션에 포함한다.

동기화 정책은 다음과 같다.

- 일반 상품 정보 변경은 커밋 후 1분 이내 검색 인덱스 반영을 목표로 한다.
- 가격과 판매 상태 변경은 검색 결과에 노출되더라도 상세 조회와 주문 생성에서 DB 값으로 다시 검증한다.
- 상품 삭제 또는 비활성화 이벤트가 늦게 반영될 수 있으므로 검색 결과 클릭 후 상세 조회에서 비활성 상품을 차단한다.
- 색인 실패는 Outbox retry와 dead-letter 정책인 ADR-007을 따른다.
- 검색 문서 재생성이 필요하면 `productId` 기준으로 DB에서 현재 상품 상태를 다시 읽어 인덱스를 재구성한다.

이 정책은 검색 결과가 짧은 시간 동안 stale할 수 있음을 인정하되, 구매와 재고 변경의 최종 판단을 DB에 남겨 사용자 피해를 줄인다.

## 적용 범위

- 현재 단계에서는 검색 엔진, 색인 워커, Outbox 이벤트 타입을 추가하지 않는다.
- Phase 3 Day 2에서 검색 인덱스 동기화 이벤트를 Outbox 기반으로 별도 설계한다.
- 상품 목록 캐시는 ADR-009를 따른다.
- 상품 상세 캐시는 ADR-010을 따른다.
- 검색 read model 도입 후에도 주문 생성은 `ProductRepository.decreaseStockIfAvailable`의 DB 조건부 업데이트를 최종 검증으로 사용한다.

## 결과

상품 검색은 당분간 DB 조회를 기본으로 유지한다. 상품 수, 검색 지연, DB 부하, 검색 품질 요구가 명확한 기준을 넘을 때만 검색 read model을 도입한다.

이 결정은 별도 검색 엔진을 성급하게 추가하지 않으면서도, 상품 규모와 검색 요구가 커졌을 때 Outbox 기반 비동기 색인으로 확장할 판단 기준을 제공한다.
